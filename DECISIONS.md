# Decisions

Judgment calls made while building v0, in build order. `[OPEN ISSUE]`
markers in the spec are listed at the bottom as they accumulate.

## Phase 1: lib/roomid.ts

1. **Two parse modes.** `parseRoomId` defaults to lookup mode: it trims
   whitespace, strips an optional case-insensitive `rid:` prefix,
   uppercases the property code and unit suffix, and folds Crockford
   confusables. `{ strict: true }` requires exact canonical form and is
   intended for registration intake, where sloppy input should be
   rejected rather than silently corrected.

2. **Crockford confusable folding.** Property codes fold I and L to 1
   and O to 0 on lookup, per Crockford base32 convention. U has no fold
   and is simply invalid. Folding applies to the property code only;
   room designators are hotel-assigned labels in plain alphanumerics,
   not base32, so remapping their letters would corrupt them.

3. **Unit suffix case on lookup.** The spec defines the suffix as
   uppercase `[A-Z]`. Lookup mode accepts a lowercase suffix and
   uppercases it, on the same forgiveness principle as the designator's
   case-insensitivity. Strict mode rejects lowercase.

4. **Canonical form preserves designator case.** `canonical` keeps the
   designator as given; `lookupKey` is the fully uppercased string for
   case-insensitive matching. The registry stores the hotel's preferred
   casing and matches on the key.

5. **Two-segment input is a structure error**, not a missing-suffix
   error. `7QM4KX92-1412` is rejected with a message showing both valid
   forms. The suffix is mandatory in v0; there is no default-to-A
   behavior, since guessing a suffix could resolve to the wrong unit.

6. **Vitest** as the test runner: fast, zero-config with TypeScript,
   standard for Next.js apps not using Jest.

## Phase 2: schema and seed

7. **Dual registry backend.** With no Supabase env vars, the app serves
   the demonstration dataset from memory, generated by the same module
   (`src/data/demo-registry.ts`) the seed script writes to Supabase. The
   site therefore runs, and can even be deployed, before a database
   exists, and the two backends cannot drift apart.

8. **Case-insensitive lookup via an index, canonical casing in the
   row.** `units` has a unique index on `upper(room_id)`; reads use
   `ilike` with no wildcards, which is index-served case-insensitive
   equality.

9. **The intake table lives in the same database but outside the
   registry.** `registration_requests` rows are requests to the
   registrar, not registry records, and are not publicly readable. The
   app remains read-only toward the registry tables themselves.

10. **Lifecycle rows in the seed.** Beyond the 40 plain units, the demo
    includes the spec's canonical example as a supersession pair
    (1412-A superseded, redirecting to the active 1412-B) and one
    retired identifier (1407-A), so all three statuses are
    demonstrable and the example everyone tries first resolves. 42
    unit rows total.

## Phase 3: resolver

11. **The resolver is a route handler, not a page.** `app/[id]/route.ts`
    returns both content types, which gives exact control of status
    codes (400, 404, 301, 429) and headers. The HTML documents are
    rendered by a template module styled to match the site. Static
    routes (/spec, /registry, robots, etc.) take precedence over the
    dynamic segment, so they can never be shadowed.

12. **Wildcard Accept gets HTML.** `*/*` alone does not select JSON;
    only an explicit application/json or application/ld+json does, plus
    the `.json` and `?format=json` overrides. Plain `curl` therefore
    gets HTML, matching the spec's wording "anything else returns HTML".

13. **429 responses are not cacheable.** The brief asks for
    `Cache-Control: public, max-age=3600` on every resolver response,
    but caching a rate-limit rejection would serve 429s to innocent
    clients behind a shared cache, so 429 sends `no-store` and keeps the
    other required headers.

14. **301 bodies.** JSON supersession responses carry the record with
    `supersededBy` in the body alongside Location. HTML supersession
    responses are bare redirects, since browsers follow them without
    reading the body.

15. **Rate limiting is in-memory per instance** (60/min/IP, sliding
    window). On serverless each instance counts separately. Acceptable
    at v0 traffic; noted in the README as the thing to swap first.

16. **Demo records self-identify.** Seeded rows return `"demo": true`
    in JSON-LD and a visible note on HTML pages, so the registry never
    appears to have adoption it does not have.

## Phase 4: specification

17. **Published as Working Draft, not final.** The working group's open
    question about embedding the door number in the identifier is
    structural, so /spec/1.0 states plainly that immutability begins
    when the status flips to Published, while committing that section 3
    syntax is stable. Marking a document immutable while its principal
    design question is open would spend the site's credibility on day
    one.

18. **Six [OPEN ISSUE] blocks** rather than invented rules:
    third-party registration of unclaimed properties (4.3), composed
    and connecting units (4.3), multi-successor supersession for splits
    (5.3), semantic versus opaque unit identity (5.6, the headline
    issue), registrar succession mechanism (7), and IANA registration
    of the rid: scheme (10).

19. **A "1.3 Out of scope" subsection** makes the identity-only
    boundary normative (MUST NOT add attributes, scores, rates,
    availability, provenance) instead of leaving it implied by the
    schema guard.

20. **Supersession chain as durable identity** (6.5): clients can treat
    any identifier in a chain as the same physical unit and follow 301s
    to the current one. This gives integrators the practical benefit of
    an opaque immutable ID under the current format.

## Phases 5 and 6: pages

21. **Design system.** Georgia serif on near-white paper, one accent
    (#1a55a0) used for links and the unit suffix segment, monospace for
    every identifier with the three segments visually distinguished,
    1px borders, no gradients, no illustration, no cards. Light mode
    only; a registry site from 2009 would not have a theme toggle.

22. **Repo link points to github.com/roomza/openroomid**, which does
    not exist yet. Create it (or edit the footer and home page) before
    launch.

23. **Intake degrades to mailto.** The /registry form posts through a
    server action to `registration_requests` using the secret key; if
    Supabase is unconfigured or the insert fails, the error message
    directs to curtis@roomza.com, which the policy text also offers as
    an equal path.

24. **The Offer example on /implement carries a price** ($189.00). That
    is correct, not a violation of the identity-only rule: the price
    lives in the hotel's own markup, and the block exists to show the
    join between a commercial offer and the identifier. The prose says
    this explicitly.

25. **`/spec` redirects 302** via next.config so the current-version
    pointer is never cached as permanent.

## Design polish pass (2026-08-09)

26. **Type system.** Source Serif 4 (display and body, via next/font)
    replaces Georgia; IBM Plex Mono replaces the system mono stack and
    carries all registry machinery: identifiers, nav labels, table
    headers, status badges, form labels, buttons. Two families total.
    Georgia and Menlo remain as fallbacks.

27. **Palette moved to OKLCH** with cool-tinted neutrals matching the
    ink-blue accent. Same one-accent discipline as before.

28. **Chrome.** Print-style masthead: bold site name over a double rule
    (2px ink, 1px hairline). Footer restructured into labeled Registrar
    and Documents columns. Buttons are mono uppercase with a 1px ink
    border; no fills, no radius, no glow.

29. **Home anatomy diagram** replaces the three-row table: the example
    identifier at display size with labeled underlines per segment.

30. **Resolver HTML pages** mirror the app design but load the two
    fonts from Google Fonts CDN, since next/font self-hosting is not
    available to a route handler's standalone documents. If external
    requests on resolver pages are unwanted, drop the two link tags;
    everything falls back to Georgia and Menlo.

31. **Print stylesheet** on the app pages: chrome hidden, links
    unstyled, so the spec prints like a document.
